## Context

See proposal.md — Why. The design constraint that shapes everything below is that **this framework has no single response-send chokepoint**, unlike Laravel's HTTP kernel. Responses leave through three unrelated paths:

- **REST routes** return a `JsonResponse` (a `WP_REST_Response`) that **WordPress's REST server serializes** — framework code never touches the send
- **Site routes** are emitted by `SiteRouter::send_response()` calling `header()` and `echo` directly (`src/Routing/SiteRouter.php`)
- **Redirects** go through `RedirectResponse::send()`, which calls `wp_safe_redirect()` and then `exit`

Other relevant existing structure:

- Services live in `src/Managers/` (`OptionManager`, `LogManager`, `EventManager`), registered as singletons in `CoreServiceProvider::register_managers()` and aliased in `Application::register_base_aliases()`
- Facades extend `Framework\Facade` and return a container alias from `get_accessor()` (`src/Supports/Facades/Option.php` is the model)
- `Framework\config()` reads `config/<file>.php` from the host app and returns the supplied default when the file is absent
- WordPress hooks are `BaseHook` subclasses listed in `HookServiceProvider::$defaults` and bound in its `boot()`
- `phpcs/Framework/Sniffs/NamingConventions/SnakeCaseMethodSniff.php` enforces snake_case method names; `phpcs.xml.dist` excludes PSR-1's camelCase rule
- The outbound client already declares an unused `'cookies' => []` option, which `wp_remote_request()` understands natively

## Goals / Non-Goals

**Goals:**

- One emission path, so a cookie behaves identically no matter which of the three response paths a handler uses
- A public API that reads like Laravel's, transliterated to this repo's snake_case convention
- Testable emission without manipulating real HTTP headers in the test process
- Zero configuration required; correct behavior on subdirectory and multisite installs out of the box

**Non-Goals:**

- Cookie encryption, signing, or an `Encrypter` service. The API is shaped so one could be added later without breaking callers
- A session driver, flash data, or anything else built on top of cookies
- A middleware kernel. The flush points are wired directly rather than introducing a pipeline abstraction
- Editing the vendored framework copy under `example/libraries/`, which is generated by `scripts/`

## Decisions

### Queue-and-flush, not immediate writes

`Cookie::queue()` adds to a queue held by `CookieManager`; a flush writes every queued cookie and clears the queue. Flush is invoked at each send point.

*Why:* it is the only model that works across all three response paths. It also preserves Laravel's semantics — a cookie can be queued by a service or middleware that never sees the response, and can be un-queued before it is written.

*Alternatives considered:* writing the header immediately on `make()`/`queue()` is simpler but breaks `unqueue`, breaks response attachment, and silently fails once output has begun. Storing cookies per-response object was rejected because WordPress serializes REST responses itself, so a per-response store would need a second retrieval path that digs cookies back out of the response inside a filter — two sources of truth to merge.

### Response `with_cookie()` delegates into the queue

`Response`, `JsonResponse`, and `RedirectResponse` share a `Framework\Http\Concerns\InteractsWithCookies` trait (following the existing `Concerns/InteractsWithFiles` pattern). Its methods push into the manager's queue and return `$this`; the response objects store nothing.

*Why:* it gives the Laravel-looking `response()->json(...)->with_cookie(...)` call without creating a second store. `JsonResponse` extends `WP_REST_Response`, whose serialization we do not control, so a per-response store would be unreachable at send time anyway.

*Trade-off:* the cookie is queued at attachment time rather than at send time, so a response that is built and then discarded still emits its cookie. This is documented; `without_cookie()` is the escape hatch.

### Four flush points

| Path | Flush site |
|---|---|
| Site route response | Top of `SiteRouter::send_response()`, before any `header()`/`echo` |
| Site route template branch | `SiteRouter::dispatch_match()`, before `include $file` |
| Redirect | `RedirectResponse::send()`, before `wp_safe_redirect()` (that call is followed by `exit`) |
| REST | `rest_post_dispatch` filter |
| Ordinary page load | `send_headers` action |

`rest_post_dispatch` is chosen over `rest_pre_serve_request` because it fires **before** `WP_REST_Server::send_headers()` and well before body output. As a filter its handler MUST return its first argument unchanged — swallowing the response there would break every REST route.

`send_headers` is a safety net for cookies queued during `init`/`wp_loaded` on ordinary page loads; it fires before `template_redirect`, so it does not cover site-route-queued cookies — hence the explicit `SiteRouter` flushes.

### Defaults resolved in three tiers

`config('cookie.*')` → WordPress environment (`COOKIEPATH`, `COOKIE_DOMAIN`, `is_ssl()`, each guarded with `defined()`/`function_exists()`) → framework fallbacks (`/`, no domain, non-secure, http-only, `SameSite=Lax`). Per-cookie arguments override all three.

*Why:* zero-config correctness on subdirectory and multisite installs, where a hardcoded `/` sets cookies at the wrong scope, while still letting a host app override centrally.

*Alternative considered:* requiring `config/cookie.php` as Laravel requires `config/session.php`. Rejected because this is a library consumed by plugins that may ship no config directory at all.

### `write()` as the single test seam

All emission funnels through one protected `CookieManager::write(Cookie $cookie)` that guards on `headers_sent()` and calls PHP's `setcookie()` with the options-array form (PHP 7.3+, required for `SameSite`; the repo targets 7.4+).

*Why:* tests subclass `CookieManager` and override `write()` to record instead of emitting, so no test manipulates real headers or depends on output buffering. It is also the one place the `headers_sent()` warning is raised.

### Request cookies in a separate bag

Cookies are stored in their own `$cookies` property on `Framework\Http\Request`, read only through `cookie()`, `cookies()`, and `has_cookie()`. They are never merged into `$attributes`.

*Why:* cookies are attacker-controlled. Merging them into `$attributes` would let a cookie satisfy or silently override a validated body field, since `all()`, the typed accessors, validation, and sanitization all read from `$attributes`. Laravel and Symfony keep cookies in a separate bag for the same reason.

*Implementation note:* WordPress's `wp_magic_quotes()` slashes `$_COOKIE` exactly as it does `$_GET`/`$_POST`, so cookie values go through the existing `Request::unslash_array()`. `make_from_http()` gains a **trailing** `$cookies` parameter so existing call sites stay valid; `make_request(WP_REST_Request)` reads `$_COOKIE` directly, because `WP_REST_Request` carries no cookie params.

### `cookie()` helper matches Laravel exactly

No arguments returns the manager; arguments build and return a `Cookie` **without** sending it.

*Alternative considered:* making `cookie('name')` read the request cookie, matching this repo's `request('key')` helper. Rejected because it inverts Laravel's meaning — in Laravel `cookie('name')` builds a null-valued cookie — and reading is already served by `request()->cookie('name')`.

### Class placement follows the repo, naming follows Laravel

`Framework\Http\Cookie` (value object, next to `Request`/`Response`) and `Framework\Managers\CookieManager` (service, alongside `OptionManager`/`LogManager`). The manager is Laravel's `CookieJar` under this repo's manager naming; its **method names** stay Laravel's, snake_cased where multi-word (`has_queued`, `get_queued_cookies`, `flush_queued_cookies`, `set_default_path_and_domain`).

## Risks / Trade-offs

- **Cookies attached to a response that is never sent are still emitted** → documented; `without_cookie()` / `unqueue()` remove them. Accepted as the cost of a single store.
- **A site route that echoes before flushing loses its cookies** → the `headers_sent()` guard skips the write and logs a warning naming the cookie, so it is discoverable in the log rather than silent. Never fatal.
- **Plain (unencrypted) cookie values** → documented prominently in `docs/cookies.md`; every requirement treats incoming cookies as untrusted input. The value object and manager signatures leave room to add signing later without changing call sites.
- **`rest_post_dispatch` runs for every REST request on the site, not just framework routes** → the handler is a no-op when the queue is empty, and returns its first argument untouched.
- **New trailing parameter on `Request::make_from_http()`** → additive with a default, so existing callers and any subclasses in host applications keep working.
- **`'cookies'` reaching `wp_remote_request()`** → the option is whitelisted in the client's existing `Arr::only()` merge, but the full path from `with_cookies()` to the transport must be read through and covered by a test rather than assumed.
